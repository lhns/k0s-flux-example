# cheogram-sip

XMPP to SIP gateway. An XEP-0114 component on one side and Asterisk on the other, so a
Conversations-family client places and takes real phone calls over Jingle. The same Asterisk
is the SIP side of the Matrix bridge.

## Shape

```
both trunks -- SIP/UDP 5060 outbound REGISTER only, no inbound forward
    |           RTP UDP 10000-10049 both ways
    |
[pod: asterisk + cheogram-sip] --XEP-0114 x2, plaintext, pod network--> snikket pod, :5347
    |
    cheogram-sip-lb, MetalLB 10.20.176.150, externalTrafficPolicy: Local, 50 UDP ports
```

One Deployment (`Recreate`, one replica), two runtime containers from **two images**:

- `asterisk`: `ghcr.io/lhns/asterisk`, our DTLS fork (below). `render-config` uses the same image.
- `cheogram-sip`: `singpolyma/cheogram-sip`, the XEP-0114 component from the JMP project.

They meet only over XMPP, through prosody, and fail differently (the binary exits when its
component connection drops; Asterisk holds live calls and reconnects). Neither runs the upstream
image's `entrypoint.sh` (it starts *both* processes, putting a second `sip.xmpp.example.com` on the
wire); `render-config` renders the config instead, which keeps credentials out of both runtime
containers' environments.

Two components, both defined in `apps/snikket/sip.cfg.lua`, neither in DNS nor in any cert:
`sip.xmpp.example.com` (user facing; dial `+49XXXXXXXXX@sip.xmpp.example.com`) and
`asterisk.xmpp.example.com` (Asterisk's `res_xmpp`).

Asterisk is not a container in the snikket pod: snikket is `Recreate` on an RWO PVC, so every
Asterisk iteration would cold-restart the chat server. A prosody restart costs the `cheogram-sip`
binary a crash-restart cycle. So does its first start: the binary dials prosody once and does
not retry, and `dependsOn: app-snikket` only orders the apply.

### prosody side

`apps/snikket/sip.cfg.lua`, via `SNIKKET_TWEAK_EXTRA_CONFIG`. Two settings are load-bearing and
fail silently:

- `component_interfaces = { "0.0.0.0" }`: otherwise 5347 binds to localhost. It must sit above
  the `Component` lines.
- `validate_from_addresses = false`: `res_xmpp` sends some stanzas with no `from` and prosody
  kills the stream; the symptom is "the first call arrives, later ones fail". Global, acceptable
  only because both components are ours.

The components are local-only (`modules_disabled = { "s2s" }`) and `apps/snikket/ldap.cfg.lua`
admits only `memberOf=xmpp` or `admin`; the line's `callers` decides the rest.

## Providers

`sip.example.net` (ExampleISP fiber): outbound PSTN, 110/112, and inbound on three DIDs across two lines.
`voip.example.org`: inbound and short extensions; currently `disabled: true`. It cannot place
outbound PSTN calls (it answers `200 OK` and plays a recorded refusal, which looks like a
connected call); PSTN refuses outbound SMS with `501 Sip Gw only`. Provider policy.

## Configuration model

`routing/` is a Helm chart whose **values are the table**; Helm checks them against
`values.schema.json`, so a malformed table is rejected at reconcile time.
`routing-release.yaml` packs it as its own ExternalArtifact (ADR 0047).

```
routing/values.yaml --helm--> ConfigMap cheogram-sip-routing   (routing.lua)
                         |      mounted at /routing, re-read per call; reloader-ignored
                         +----> ConfigMap cheogram-sip-pjsip   (pjsip.conf, rtp.conf)
                         |      copied by render-config, read once at start; rolls the pod
                         +----> ConfigMap sip-line-members     (reflected into matrix)
```

`pbx_lua` re-executes `extensions.lua` per call, so a routing edit is live once kubelet refreshes
the volume, without a restart, and a malformed table fails closed. `cheogram-sip-pjsip` is read
once at start, so an edit rolls the pod.

**Generated by the chart** from `values.yaml`: every pjsip object of every registration
(`routing/templates/_pjsip.tpl`), the transports, and `rtp.conf` (`routing/files/rtp.conf`, from
`rtp.start/end` and `external_address`), so the public IP lives once in `values.yaml`. Only the
two in-cluster peers, `[livekit]` and `[matrixbridge]`, are written by hand, in
`routing/files/pjsip-in-cluster.conf` (templated for `bridge_host`).

Fixed config (`*.conf`, `extensions.lua`) is the `cheogram-sip-config` ConfigMap. `render-config`
copies everything under `/config` and `/pjsip`, so a new fixed file is one line in the
`configMapGenerator` in `kustomization.yaml`.

`cheogram-sip-lb` still lists the 50 RTP UDP ports by hand: moving the Service into the chart
would prune and recreate it and flap the VIP. `tests/check-routing.py` asserts the list equals
`rtp.start..rtp.end`.

The Matrix bridge host is the single value `bridge_host`: it feeds the `[matrixbridge]` AOR
contact and `routing.lua`'s `bridge_host`, which `extensions.lua` uses for the SMS Request-URI.
The peer name is the constant `matrixbridge` in `extensions.lua`.

### Registrations

**The entry name is the pjsip object-set name,
the dialplan's `peer`, and the name of the Secret key holding its password.** The Secret
`cheogram-sip-registrations` (`secret-registrations.yaml`) is mounted whole at `/sip-secrets`, so
adding a number or a provider is one entry plus one Secret key of the same name. Values render
into a plaintext ConfigMap and hold no passwords (`scripts/check-substitution.py`).

`render-config` scans `pjsip.conf` for `#include <key>-secret.conf` and writes
`password=<Secret key value>` into each; a missing or empty key stops the pod. Livekit's include
is `livekit-password.conf`, from the `livekit-sip-trunk` Secret.

- **One object set per entry**, never per host: `from_user` is pinned per endpoint, and a
  registration is the finest thing pjsip attributes an inbound call to.
- **`user`** is the account, the `from_user` and the Contact user part the carrier echoes, which
  inbound keys on; (`host`, `user`) must be unique. It cannot contain `@`: the whole
  `type=registration` object would fail to load (one sorcery error at startup, then silence).
- **`disabled: true`** keeps the entry and its Secret key but renders no object. A line whose
  `primary` is disabled is off: every rule or `#<line>` label reaching it is **refused**
  (`line '<name>' is disabled`), never passed to the next rule, and nothing inbound attributes
  to it. An emergency route or `entrypoint` may not be disabled.
- **`entrypoint: true`** marks the host's default registration (at most one; unneeded for a host
  with one). An inbound call nothing else identifies is attributed to it, so per-DID inbound
  degrades to one line, not nothing, and it alone carries the host's `type=identify`. Its
  `user` and `host` are `SIP_USER`/`SIP_HOST` in `cheogram-sip.env` (held together by the tests).

### Tests

`tests/run.sh` (convention in `../../README.md`). `check-routing.py` asserts behaviour of the
rendered output, not the YAML text of `resources.yaml`/`kustomization.yaml`: object sets,
identify and default rules, includes, table invariants, schema enforcement via Helm,
`line_members`, re-enabling, the RTP range. `dialplan_test.lua` runs `extensions.lua` under Lua 5.1. Test phone numbers are placeholders.

## The Asterisk image

`ghcr.io/lhns/asterisk`, built by <https://github.com/lhns/asterisk> from branch
`22.11.0-cheogram-dtls`: Asterisk 22.11.0 plus commits giving `chan_motif` DTLS-SRTP (XEP-0320),
RTCP-MUX and the ICE-UDP interop they need, `res_xmpp` the matching disco feature, and a fix for
upstream `chan_motif` handing stack garbage to ao2 when it negotiates a Jingle description.
Without them no encrypted Jingle call completes. DTLS is opt-in per endpoint
(`dtlsenable=yes` in `motif.conf`). Upstream-based branches: `chan_motif-dtls`,
`chan_motif-codecs-init`.

Digest-pinned; a newer Asterisk is a rebase in the fork, then a pin bump. **After a digest bump
re-diff `extensions.lua`** against the upstream image's copy: the component half still comes from it.

The image has no `/etc/asterisk`:

- **`/etc/asterisk` is ours entirely** (Memory-backed emptyDir; passwords are rendered there). A
  config file Asterisk wants and does not find leaves its module on defaults. There is no
  `asterisk.conf` on purpose: the built-in paths are the same, and each `asterisk -rx` prints one
  "using built-in defaults" line.
- **Asterisk EXITS without `modules.conf`**, with nothing else in the log. `pbx_config` and
  `res_pjsip_config_wizard` are noloaded for behaviour. The rest of its `noload` list is modules
  that log an ERROR at boot for a config file we do not ship; after a bump, boot without the
  list and keep what logs an ERROR.
- **There is no `default` context** (`pbx_config` is noloaded). pjsip has no `[general]`, so
  `context=public`, `message_context`, `identify_by` and the NAT options are per endpoint
  (`_pjsip.tpl`); a missing one is silently wrong.
- **`CHANNEL(peername)` and `SIP_HEADER()` read nothing here**; use `CHANNEL(endpoint)`/`PJSIP_HEADER`.

## Outbound gate

**`lines.<name>.callers` is the whole of outbound permission.** A destination resolves to a line
(by routing rule, `#<line>` label, or a bare trunk label's default registration) and
`line_permits` asks that line's list whether this caller may present it. It **refuses**
(`kind = "forbidden"`, no peer) and does not fall through to another line, so revoking someone is
one edit and cannot leak. It fails closed: no `callers`, an empty list, an unknown line or an
unidentified caller all refuse. A refusal logs `Cannot dial '<to>': caller is not in the callers list of line '<line>'`.

`from_glob` is **not** this: it narrows which rule applies and falls through. An
`emergency` rule pins a registration rather than a line, so no `callers` list is consulted and
110/112 stay reachable from an account permitted nothing else; the only ungated path, hence the
digits-and-classes limit on its `to_pattern`.

No live call has been refused, and a silently open trunk looks like a working one.

### Destinations and rules

`SIP_HOST` (PSTN) is the PSTN trunk the `cheogram-sip` binary appends to a bare number. The
dialplan strips a host equal to `SIP_HOST` before routing, so short extensions still reach their
own trunk.

| dialled | goes |
| --- | --- |
| no label | the first matching outbound rule |
| label naming one of our trunk hosts (`SIP_HOST` and every enabled registration's `host`) | that host's default registration |
| label naming a **line** | that line's primary registration |
| anything else | **refused** |

The last row is fail-closed: nothing falls through to an uncredentialed `SIP/<user>@<label>`
dial. There is **no default line**: `#<host>` is not a line name. With the table missing or
malformed the dialplan finds no peer and refuses.

**`to_pattern` is a Lua pattern, not a regex.** A regex would not error, it would match nothing
and fall through. The schema rejects `{ } |` and backslash; spell out counts (`%d%d?%d?`). The
renderer anchors each as `^(...)$` once, so `11[02]` cannot match `0112345`.

## Lines and identity

A **line** is an identity namespace: three DIDs share one host, so the host cannot say which
rang, the line can. Membership is `registrations.<k>.line` only. `primary` is the member the
line *presents* outbound (Ofcom's Presentation Number, as against the Network Number the carrier
transmits regardless); its endpoint must pin that number, which the tests check.

A caller is rendered `<line>-<digits>` to Matrix (portal `office-4915112345678`, conference
`sip-office-+4915112345678`) and `+4915112345678#office` to XMPP; the XMPP form is also how a
client dials back. Split a portal ID with `^(.*)-([0-9]+)$` so line names may contain hyphens;
`-` and not `_`, which mautrix escapes to `=5f` in an MXID localpart (the schema rejects it).

`lines.<name>.members` (literal `matrix:@user:server`) gives Matrix users the line's space and dial
room without being rung. The chart derives the bridge's `line_members` (literal `matrix:` ring
targets plus `members`; none for a disabled line) into `sip-line-members`, reflected into `matrix`.

The emergency rule pins a registration because the presented number fixes the address the
dispatcher sees.

**Per-DID inbound trap.** It rests on the carrier handing back the `;line=` token pjsip puts in
our Contact, or the Contact user in the Request-URI: observed or hoped-for behaviour, not a
standard (`;line=` echo is untested for this carrier). If both stop, inbound collapses to the
host's default line, which looks like a correct match except that it logs `inbound fallback:`.

Matrix outbound uses the room's line from the conference name and does not consult `to_pattern`
(emergency numbers excepted); a conference with no line routes by `to_pattern`, an unconfigured
line is refused.

## Caller ID is normalised to E.164

Carriers name one human `+49...`, `0049...`, `0...` or bare, which would give several JIDs and
portal rooms. `extensions.lua` collapses the number on both inbound paths (calls and SMS),
driven by `SIP_E164_COUNTRY`. It is in the dialplan, not a `normalize-cid` gosub, because the
dialplan keys off `SIP_HEADER("From")`, not `CALLERID(num)`.

Ordering traps: anything at or below `SIP_SHORT_MAXLEN` is left alone (or 110 becomes `+49110`),
and `00` is tested before `0`. `SIP_E164_AREA` is deliberately empty: a bare number is either
national with the trunk `0` omitted or a subscriber number missing its area code, nothing tells
them apart, and setting it corrupts the first kind. Leave it until the `normalize_e164:` NOTICE
lines show what the carrier sends.

## Caller JIDs use `#`, not `\40`

A SIP address must fit a JID localpart, which cannot hold `@`. We use
`5551#voip.example.org@sip.xmpp.example.com` rather than XEP-0106's `5551\40voip...`: `#` is legal
in a localpart and one of the few characters RFC 3261 forbids unescaped in a SIP user part, so
splitting back is unambiguous (a dot would not be). Cost: `#` starts a URI fragment, so a JID in
an `xmpp:` URI must be percent-encoded. `sip_uri_to_local` and `local_to_sip_uri` are the two
ends; change one and calling back breaks.

The host in that JID is the **line name**, not the carrier's `From` host (an SBC IP for
eventpbx): it says which of our numbers rang, survives renumbering, and is dialable back
through the credentialed peer. Not a reverse DNS lookup, which would put a resolver in the call path.

## Router

Forward UDP 10000-10049 to `10.20.176.150` (RTP, both the trunk and the Jingle leg). **Not 5060**:
Asterisk registers outbound and inbound INVITEs return down that pinhole.

**The PSTN path needs a route as well as a srcnat.** ExampleISP carries telephony on its own VLAN (232;
internet is 132) and `10.21.0.11` is inside the carrier network. Both are needed: a route
sending `10.21.0.0/16` out the telephony VLAN interface, and a srcnat to that interface's DHCP
address (`10.100.x`). A srcnat alone leaves routing unchanged, so the packet leaves via the WAN
with a VLAN address and the ISP drops it as spoofed: total silence with conntrack still counting
replies. Confirm by `received=` in the registrar's answer: the `10.100.x` address, not the CGNAT one.

The RouterOS SIP helper (`/ip firewall service-port sip`) is disabled: it conflicts with
Asterisk's own `external_*_address`.

Snikket itself needs TCP 5222 and 5269 forwarded to `10.20.176.210`; 5269 carries the push that
wakes a backgrounded phone for an incoming call.

### Addressing quirk

The advertised address (`external_address`, a static address arriving through a tunnel) and the
egress address (the DS-Lite CGNAT address) differ, so a far end that latches onto our source
(comedia, ICE peer-reflexive) and one that obeys our SDP send media to two different places.
Both work; it is a standing source of one-way audio. Asterisk deliberately does not use the
shared coturn (static TURN credentials vs. its time-bounded HMACs).

## The Matrix bridge

`matrix-sip-bridge` (`apps/matrix`) is an ordinary SIP peer, `[matrixbridge]`, not an AMI
client, and **static**: it never REGISTERs, so its AOR contact names its Service, with
`;transport=tcp` because SIP MESSAGE over UDP fragments and is dropped (and pjsip takes the
transport from the contact). The endpoint name must equal `sip.username` in the bridge's config.
The bridge authenticates only `REGISTER`, so its INVITEs and MESSAGEs arrive unauthenticated from
a pod address that is not the AOR contact: `identify_by=username` is the whole match and the
endpoint has no `auth`. What keeps anything else in the cluster from claiming the name is `vnet.yaml`.

`message_context=messages-in` is on every endpoint, trunks included, so every out-of-call
MESSAGE lands in that dispatcher (see SMS).

### Inbound calls into Matrix

An inbound trunk call rings the call plan of the line whose DID was dialled
(`lines.<name>.inbound_route`): stages tried in order until one answers. A stage's `ring`
targets share **one** `Dial()`; Asterisk times a whole `Dial()`, so **total ring time is the sum
of the stages**, and the bridge's `calls.ring_timeout` must stay above any total the plan can
reach. A `record` stage is terminal and, with no voicemail in this image, ends the call. A
`tel:` ring target is **refused**: it would originate a trunk call from inside an inbound one,
with no caller identity to gate, no cap on trunk channels, a recorded refusal or mobile voicemail
read as an answer, and a loop if it forwards back to a DID.

Each distinct literal `matrix:@user:server` is **one leg**, `Local/<hex of lowercase MXID>@matrix-leg/n`
(an extension cannot hold `@` or `:`); a bare `matrix:` is `Local/default@matrix-leg/n`, the
bridge's default recipient. `matrix-leg` dials `PJSIP/<caller>@matrixbridge` with a `b()` pre-dial
gosub that sets `X-Conference: sip-<line>-+<E.164>` and `X-Matrix-Recipient: <mxid>`; that is the
only place `PJSIP_HEADER(add)` writes the outbound channel, hence the Local leg. The bridge names
the portal room from the conference header and declines one it does not recognise, so a mismatch
with `calls.conference_prefix` fails closed and silently. An unattributed caller gets no Matrix leg.

Asterisk constraints, detailed in `extensions.lua`: a channel in `ConfBridge()` cannot `Dial()`,
so the order is Dial first; `U()` with `GOSUB_RESULT=CONTINUE` is mandatory because the bridge's
leg carries no media; and `Dial()` hangs the other legs up with `ANSWERED_ELSEWHERE` when one
answers, so the bridge answering is what cancels the XMPP legs and it must not answer until a
Matrix user has joined. The `matrix-answered` gosub also runs on XMPP legs and app_dial hangs the
answered leg up if it fails, so it is in `pcall`.

`confbridge.conf`: livekit-sip is the marked user and the caller `end_marked`, so a Matrix hangup
ends the caller; the other direction is the `h` extension calling `ConfKick()`.

### Outbound calls from Matrix

The bridge INVITEs `sip:<E.164>@cheogram-sip-internal...` from `[matrixbridge]` with the same
`X-Conference`; reaching `context=matrixbridge` requires that peer, the only authorisation here.
The far end must end up in the **conference**, not the bridge's media-less control leg, so the dialplan uses `Originate(...,exten,matrix-outbound,<conference>,1)`, which blocks and
sets `ORIGINATE_STATUS`, the only way to answer with a real SIP status. The 200 is withheld until
the far end answers (the bridge asks livekit-sip to join only after that). Failures map to
responses: bad number or conference header 404, no trunk 503, busy 486, no answer 480.

Trunk selection is `resolve_destination`, shared with the XMPP path, with the room's line as a
label. Every endpoint pins `from_user`, so the presented number is the chosen peer's whatever
`CALLERID` says.

### SMS

`messages-in` is a **dispatcher** for both trunks and the bridge. A message is outbound only when
the `From` user is the bridge peer **and** the extension is a bare number; on `From` alone a
carrier-injected `From: sip:matrixbridge@…` would be an outbound-SMS primitive billed to us.

Inbound goes to the people the line's call plan rings: one XMPP message per distinct `xmpp:`
target (a line with no call plan keeps the dialled contact) and one bridge message per Matrix
recipient (`X-Matrix-Recipient` via `MESSAGE_DATA`), XMPP first. The bridge leg needs a sender that normalises to `+E.164` (the bridge drops
a number without one *while answering 200*), derived via `matrix_conference_name` so an SMS and
a call from one number share **one** portal room. A Message channel has no endpoint, so the line
comes from the dialled contact; without an echoed Contact it falls back to the default
registration and logs `how=[entrypoint]`.

Outbound reuses `resolve_destination` and sends with no `from`, so the endpoint's `from_user`
applies. No allow-list or rate limit: the boundary is the `[matrixbridge]` peer plus the
numeric-destination check. Today it is dead (PSTN answers `501`); inbound SMS works.

Silent failures: Asterisk answers `202` before the dialplan runs, the bridge answers `200` for a
message it drops, and `MESSAGE_SEND_STATUS=SUCCESS` means handed over, not delivered; the
`sms inbound`/`sms outbound`/`xmpp outbound` NOTICE lines are the observability. The bridge caps
a MESSAGE at 20480 serialised bytes, with no segmentation.

## 110/112 and voicemail

110 and 112 are configured but are not the emergency plan: this is VoIP behind DS-Lite CGNAT,
prone to one-way audio and to trunks that stop registering when a route changes. A mobile is.

Voicemail is a `record` stage that records nothing: `app_voicemail` declines to load without
`voicemail.conf`. The plan (record a file, have the bridge post it as a Matrix voice message;
Matrix only) is in `kube-cluster/TODO.md`.
